# 可直接交给其他 Code Agent 的完整开发 Prompt

使用方式：把本文件下方正文完整复制到另一个 Code Agent，并让它打开本项目根目录。规格文件应随仓库一同提供，不需要本聊天历史。本文是给执行 Agent 的指令，当前编写/验证 Prompt 本身不代表产品实现完成。

---

你是 domimap 的主要开发 Agent。请立即检查当前仓库并持续实施以下目标，完成规格、代码、集成、自测与真实比较。不要只给方案、只实现演示或在每个小步骤后询问是否继续。

## 一、最终目标与不能删掉的范围

建设生产级本地知识库，连接 Java 多仓代码、项目文档、独立文档目录、Markdown vault 和人工知识；人及 Code Agent 使用同一可信检索/保存服务。借鉴 claude-obsidian、Codebase-Memory-MCP、CodeGraph、Graphify 的设计，不要求同时集成四套后端。

必须完成：

1. 来源/实体身份、适用范围、版本化可读证据、正确关系与覆盖缺口。
2. 可恢复构建/更新、事务化人工知识、修订/审定/撤回、变化复核、导出/恢复/保留/删除。
3. Claude Code、Codex、用户实际使用的 ZCode 和 DSH Code Agent 四客户端快速接入与真实联调，各自验证，不能用通用 CLI/mock 代替。
4. 无模型也能用的人工 CLI/JSON 与本地搜索、来源阅读、知识维护页面。
5. 可信 AGENTS.md/SOUL.md 规则/人设加载、作用域、预算、生效诊断与原生桥接。
6. 时间降权、有效期、替代、未知日期、复核绑定版本和历史查询，避免复制/touch 使内容变新。
7. 声明支持的格式、框架、平台、并发、资源限制、升级/回退、安全、备份、安装与开源分发验证。
8. 最终在冻结目标任务集、相同模型/宿主/预算下，Hit@5、任务 Accuracy 和事实 micro-F1 各自严格高于上述四个竞品，并满足成对置信门槛。

首发为本机单所有者、多 Agent 会话并发；团队远程服务是后续独立范围。不要擅自扩成云平台/通用 Agent 运行时，也不要以这个边界删掉四客户端或人工维护能力。

## 二、开始前必读并核对真实状态

按顺序读取：

- `AGENTS.md`
- `specs/product.md`、`specs/workflow.md`
- `specs/requirements.json`、`specs/acceptance.json`、`specs/progress.json`
- `specs/benchmark.md`、`benchmarks/protocol.json`、`benchmarks/README.md`
- `docs/roadmap.md`、`docs/implementation/step-by-step.md`、`docs/architecture.md`、`docs/capabilities.md`
- 当前核心实现、测试、构建文件和存在的 `out/handoff.md`。

最新用户指令与宿主规则优先；规格定义目标/验收，路线定义顺序，设计定义方案，archive 只作历史。发现矛盾先定位并修正受影响规格，不能任选容易完成的一版。

当前实现是 v0.4.0 原型，有已知身份、恢复、协议和扫描边界缺陷。现有测试通过不等于生产通过。不要假设有 Git、CI、许可证文件、真实客户端或竞品运行记录；实际检查后记录状态。

## 三、执行方式：每个切片先规格，再实现

1. 为当前最小有用切片建立 `specs/tasks/<id>.md` 与 JSON，使用 task-template；明确关联需求/验收 ID、问题、契约、反例、准确修改文件、测试与回退。
2. 在 Git 建立可追踪基线；有用户未提交修改时保留，不重置覆盖。不要借初始化提交业务资料或秘密。
3. 对行为变化先形成有意义的失败案例，再实现正确契约；旧错误语义的测试要按独立来源修正并记录理由，不能按当前输出反向修改 gold。
4. 一次只迁移一条可验证路径，保持现有功能可运行。身份统一入口→关系接线→证据/发布→公共服务→保存，避免整库一次重写。
5. 运行相关单元/契约、必要的集成/负例与全部本地回归；检查任务 diff 范围，收集当前源指纹、真实日志/工件和结果。
6. 更新 progress 到实际状态。只有当前证据支持的案例能 verified；阶段必须满足全部依赖和案例。
7. 对照规格继续找缺口并实施下一片，直到全部需求完成。不要把计划、文档、脚手架、mock 或单条 demo 当成产品完成。

日常入口：

```bash
make verify
python3 -B scripts/check_specs.py --task specs/tasks/<id>.json --base <local-git-ref>
python3 -B scripts/check_specs.py --fingerprint
python3 -B scripts/check_specs.py --stage M1
```

普通可逆本地开发、测试、修复和必要文档调整直接推进。只有缺失信息/权限/运行环境真正影响下一项时才询问，说明具体需求；继续其他不依赖该答案的工作。

## 四、按优化路线执行全部 M0–M5

- **M0**：工程/Git/来源许可/构建安装/CI；需求与验收可追踪；比较协议、独立数据/标注和五系统适配 spike；最小接口及 MCP SDK 兼容小试。M0 不能以生产功能全部完成为前置。
- **M1**：登记根与捕获字节→身份/范围→有限解析试验→正确关系→固化证据→SQLite 元数据与 generation 发布→失效/中断/损坏恢复。无 Git 也必须保留可引用旧证据。先正确全量/手动更新，再优化。
- **M2**：公共 Query/Read/Trace/Context→代码/文档分路召回→范围/去重/争议/预算→CLI/MCP→只读 UI→第一条真实 Agent→上下文与文档时间→十个真实任务。人工知识只留接口，到 M3 接入。
- **M3**：note/claims/事务→幂等/冲突/审定→依赖变化和复核→手动维护页面→Markdown 交换→备份/空目录恢复/保留。至少十条知识走完跨会话使用和变化复核。
- **M4**：四客户端完整联调、格式与框架矩阵、可选监听/增量恢复、并发/安全、平台/extras、升级/回退与资源测量。可与 M3 独立推进，但最终二者都要完成。
- **M5**：冻结 RC/确认批次→真实五系统比较→独立裁决与统计→生产故障/24h 负载/恢复→净化分发物和完整证据收敛。

每步的详细输入/输出、反例和选择理由都在 step-by-step。不要为了先完成 UI 而绕开可信来源，不要为了满足某个模式而删除其他明确需求。

## 五、竞品质量是最终硬门槛

严格执行 specs/benchmark.md 和 protocol.json：

1. 对象固定为 AgriciDaniel/claude-obsidian、DeusData/codebase-memory-mcp、colbymchenry/codegraph、Graphify-Labs/graphify。按比较日期选择合理的正式版本，固定不可变 SHA/依赖，完成实际安装和健康检查；不能挑已知坏版本。
2. 相同资料、问题、宿主/模型快照、公共任务提示、工具/阅读/上下文/生成预算与五种子；接口不支持 seed 就记录限制并做五次同条件实际运行。各产品正常原生工作流可按同等 dev 机会调好再冻结。tiny dev 先估成本，使用已授权资源；不足时继续其他工作并明确缺口，不自动购买额度或缩减正式分母。
3. 确认集至少 300 可回答、100 不可直接回答、20 独立项目族 cluster；四类可回答任务各至少 50。开发与确认按来源族隔离，gold 不放进实现 Agent 可读目录。
4. Hit@5 只看前五个主证据位置；Accuracy 要求完整正确、适用且有支撑；micro-F1 对必要事实 TP/FP/FN，错误/不支持/错版本均受罚。第六项、卡片文字、名字包含不能补分。
5. 保留五系统所有题/种子，包括真正运行中的失败；环境/安装缺失意味着比较未完成，不能给竞品零分。
6. 独立盲化标注与裁决，保留原文、source/span 映射、raw/judgment 工件及哈希。模型可辅助，但不能自称正确或自己生成自己的 gold。
7. 对四基线×三指标的 12 项差值做成对 cluster bootstrap，至少 20,000 次，家族单侧 alpha=0.05/Bonferroni；每项点差和下界均 >0。候选系统还需达到绝对质量底线与负例处理要求。
8. 打平、置信区间跨零、竞品满分、缺少环境或 gold 都不能改成通过。提示词无法保证严格超越；若尚未达标，就真实报告差距并继续合理研发，不制造数字。

差距定位按摄入/身份/解析/召回/排序/证据/推断/生成/时效维护分层，先看错误样本和消融再改实现。只用 dev 调参；不要反复看同一确认集直到显著。需要新确认批次时预先登记并保持独立，控制多次检验。

## 六、自测与完成判据

必须包含：身份碰撞/重载/方法边界、源删除/旧证据、无 DDL 表关系、不同范围、文档饥饿/副本占榜、图方向/预算、非法 MCP 后有效请求、源路径越界/UI 注入/跨站、事务中断/并发/幂等/冲突、迁移/恢复/删除、上下文/时间、四客户端真实运行、已声明格式/平台、包安装和压力。

新测试必须证明需求和真实故障；不能只断言实现细节或写永远为真的镜像测试。测试产物进入临时目录/out，按需清理，不能污染源码或改写历史证据。

最终执行：

```bash
make verify
python3 -B benchmarks/evaluate.py --bundle out/benchmark/bundle.json --output out/benchmark/report.json --release
make release-check
```

当前 release-check 应因真实功能/证据未完成而失败，不能把它改为默认成功。最终通过需要全部案例、M0–M5、当前指纹/工件、真实比较和独立生产检查；评分器验证 JSON 结构与哈希不代表自动证明人审独立或语义正确。
