## 二、逐份详细分析

### D1 深度分析报告：四种互补范式

**分析对象**（按星数最高同名仓库克隆，2026-10-15 时点）：

| 工具 | 一句话定位 | Stars | 核心路线 |
|---|---|---|---|
| claude-obsidian | Obsidian 第二大脑的"可信写入层" | 15,540 | 纯 stdlib Python 事务引擎 + 15 个 Skill 提示词 |
| codebase-memory-mcp | 高性能代码智能 MCP 服务器 | 46,601 | 纯 C 单二进制 + 162 语法 + 手写 SQLite 页写入器 |
| codegraph | 常驻守护的代码图检索引擎 | 74,107 | TS + Rust 内核 + WASM，文件事件 watch 增量 |
| graphify | 万物知识图谱（代码+文档+PDF+图片） | 126,562 | Python，AST 零 LLM + 可选 LLM 语义（信封模式） |

**方法论可信度**：150 遍独立进程从头分析、SHA-256 指纹一致性审计 PASS、951,364 条信号每条带 file:line 证据。这是少见的"可复现竞调"，结论可信度高于一般 LLM 调研。

**核心结论**：四家不是竞品而是互补范式——人写知识的安全治理（claude-obsidian）、机器读代码的极限性能（cbm）、给 agent 的供给侧检索设计（codegraph）、异构语料统一图谱（graphify）。

**四家共识**（本方案设计原则的来源）：①确定性优先（结构事实出自 AST，LLM 只做语义）；②三级置信贯穿（EXTRACTED/INFERRED/AMBIGUOUS）；③token 经济（agent 是一等公民）；④本地优先（零出网默认）。

**关键分歧**：知识是人写还是机生；MCP 工具面宽（cbm 17 个）还是极窄（codegraph 1 个 explore）；增量靠原生事件还是 manifest；要不要向量。

### D3 选型决策：为什么最终"纯自研轻量版"

11 项 Java 架构师能力矩阵（源码取证）的关键发现：

1. **没有任何一家能独立担纲 Java 架构师**，且缺口正是国内刚需：
   - RocketMQ 注解 synthesizer —— 四家全无
   - @DubboService/@DubboReference 显式边 —— 四家全无（codegraph 的 hub 接口近似不够精确）
   - "页面 API 调用 → Controller"跨端连线器 —— 双侧有节点、缺连线规则
2. MyBatis 是 codegraph 独有强项（mapper XML→SQL→表列），MIT 可移植
3. 文档摄入（pdf/docx/xlsx）只有 graphify 全
4. 中文支持最强是 claude-obsidian 的 CJK n-gram 内建

**实际走的路线**（D4 与交接胶囊证实）：没有按 D3 原计划 fork graphify 当基座，而是**纯 Python stdlib 零依赖自研 lite 版**——正则/XML 规则扫描替代 tree-sitter AST。这个偏离是理性的：目标是国内 Java 栈的确定性规则（注解/XML 都是高度结构化的），不需要 162 语言通用性；换来零安装摩擦（`python3 -m domimap` 直接跑）。D2 中的 graphify AST 引擎降级为可选升级路径（P1 待办）。

### D2 自研方案 v1.0：设计蓝图要点

- **三场景三验收**：需求识别（20 个历史需求回放 Top-5 命中 ≥80%，≤30s）；问题排查（10 个历史故障根因链路前 5 命中 ≥7，≤60s）；领域地图（抽样 100 服务标签准确率 ≥90%）
- **四层架构**：采集（git mirror+文档+观测）→ 构建（AST+synthesizer+LLM 语义+领域打标）→ 索引查询（统一图+FTS5+MCP）→ 消费（三场景+Obsidian 导出+MCP 客户端）；治理横切（收缩闸门×4、增量收敛测试、覆盖缺口面板、审计账本）
- **图 Schema**：12 节点型 × 14 边型，全部带三级置信 + provenance；节点 ID = `{repo}_{path}_{symbol}` 防幽灵重复；观测边（OBSERVED_CALLS）与静态边分离
- **领域三步法**：先验种子（确定性）→ Leiden 图社区（结构）+ hub 排除 → LLM 校准（命名/冲突裁决）
- **12 条"抄作业"清单**：每条注明来自哪家、落到方案哪一层（这是 D1→D2 的价值萃取，全部可指认）
- **10 周三阶段**：P0 MVP（W1-2）→ P1 全量（W3-6）→ P2 场景化+治理（W7-10）
- **量化验收表**：7 项指标全部有测法（含"增量=全量重建，边误差 ≤5%"）

## 三、命名记录（2026-10-16 定案：domimap）

### 过程

1. 原占位名不可用：GitHub 上同仓库名重名数以万计（GitHub API 实测），不可注册、不可辨识。
2. 三重核查（GitHub in:name+全文 / PyPI / 全网产品商标）候选名。
3. **domagraph 被剔除**：GitHub/PyPI 虽可注册，但 domagraph.com 是已上线同名商业产品（"域图"·Agent 判断追踪平台），有产品/商标冲突风险。
4. javatlas / domimap / cangtu / repomundi 四个候选全部干净。

### 定案：domimap（Domain + Map）

- GitHub 无精确重名（仅 2 个模糊匹配且非同名仓库）、PyPI 可注册、全网无同名软件产品
- 直指招牌功能"领域地图"（domain 命令），语言中立（未来可扩展 Go/Python 仓）
- 与口号"百仓千档，一图识域"同构

### v0.3.0 改名执行记录（2026-10-16 已完成）

- 目录与包统一为 `domimap/`；CLI `python3 -m domimap`
- MCP serverInfo `domimap/0.3.0`；图 schema `domimap.lite.v1`
- manifest 版本门控键 `tool_version`（旧产物已删除重建）
- README/Makefile/setup.sh/tests/docs 全部同步；业务工作区路径与真实仓扫描产物已清除，工具内不含任何被分析仓库的业务数据
