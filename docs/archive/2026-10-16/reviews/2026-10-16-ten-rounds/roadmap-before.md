# domimap v0.5–v0.8：知识库演进路线

状态：**十轮复核前的历史快照，已被后续版本替代**。原制定日期：2026-10-16。

归档说明：本页仅调整了历史状态与相对链接；当前执行入口见[十轮优化路线](../../plans/2026-10-16-v0.5-v0.8-知识库演进路线.md)。

依据：[方向复核](../2026-10-16-direction-review.md)、[本地诊断结果](../2026-10-16-baseline-audit.json)。替代旧计划中关于下一阶段顺序的建议；不改写 v0.4 的历史执行记录。

## 产品目标与边界

面向 Java 研发团队，把多仓源码、项目文档、架构决策和故障结论连接为可追溯、可维护、可复用的本地知识库。保留 CLI/MCP 与现有框架规则。

第一条完整用户路径：

> 输入“订单改价如何防止并发覆盖” → 找到相关源码与文档片段 → 看清依据和未知项 → 保存一条有出处的结论 → 人工补充业务约束 → 新会话再次命中 → 源变更后标记待复核。

该路径是 v0.6 的主验收，不能只靠建出更多节点替代。当前阶段覆盖本地单用户；共享编辑、权限隔离与云托管在明确需求后单独立项。

## 阶段安排

| 阶段 | 用户能得到什么 | 前置与完成条件 |
|---|---|---|
| v0.5 可信底座与评测基线 | 同名对象不串仓，来源可定位，更新状态可信 | 先通过结构与发布一致性门槛；形成严格指标基线 |
| v0.6 知识积累最小闭环 | 查证据、保存、审定、修订、复用、失效提醒 | v0.5 通过；完整走通上述用户路径 |
| v0.7 Java 精度与规模提升 | 更可靠的调用关系、更快的变化更新 | 解析器比较后接一个后端；性能改造由测量触发 |
| v0.8 本地使用体验与试点发布 | 能浏览来源、领域、知识与待审事项 | 核心闭环稳定，并经过真实任务试点 |

工期在 v0.5 诊断修复及试点样本确定后重估，避免沿用旧“10 周”时间表作为交付承诺。各阶段按验收推进；可先交付较小切片。

## v0.5：可信底座与评测基线

本阶段不整体重写扫描器；保留可运行路径，先修会污染知识结果的契约。

### 5.1 来源和标识（P0，首先执行）

- [ ] 新增版本化工作区配置 `domimap.json`，登记稳定 repo_id、根目录、包含/排除规则与可选服务/数据源映射；禁止仅靠 basename 区分仓库。校验重复 ID 和重叠扫描范围。
- [ ] `lite_scan.py` records 携带 repo/module、source_id、owner、可解析签名与源位置。无法完整解析时分开保留候选、报告不确定性，不按方法名合并。
- [ ] `graph.py` 统一标识生成：源码实体按仓库/模块/源文件/owner/签名分隔；路由按服务和 method/path；前端引用按来源文件和调用点。表、Topic 默认按数据源/消息系统范围隔离，跨仓共享由显式映射建立。
- [ ] 文档按来源身份保留；`add_node` 对冲突的来源或 kind 报错或记录冲突，禁止静默替换正文。
- [ ] 新图升级 schema 到 `domimap.graph.v2`，记录 schema/extractor/config 版本。旧图提供明确的重建提示；新构建支持仓库无 Git 的情况。

涉及：`lite_scan.py`、`graph.py`、`batch.py`、CLI，以及新增配置/身份模块。所有依赖旧 ID 的 synthesizer 和测试一起迁移。

验收：两个仓的同名类、两个类的同名方法、重载方法、同路径文档、同 basename 仓库、同 URL 的不同服务、不同数据源同名表均不误合并。显示名仍可重复。

### 5.2 图关系与来源（P0）

- [ ] 构建分为“登记所有节点 → 解析关系 → 打标”，消除无 DDL 时丢 SQL 读写边的问题。
- [ ] CALLS 与 MQ 发送提取使用可确认的方法边界；不能可靠确认的调用不输出确定归属。添加“方法 B 的调用不能出现在方法 A”反例，不只检查有某条边。
- [ ] RPC 按接口完整身份和显式配置解析；多 provider、版本/group、别名及未解析引用保留候选，避免最后一个 provider 覆盖。暂未支持的构造列为覆盖缺口。
- [ ] 前端路由匹配同时校验服务范围、HTTP method 与路径规则；多个候选时不取第一个当确定结果。
- [ ] 节点与关系关联证据 ID；源码证据包含仓库、相对路径、行区间、源哈希和规则版本。只有可靠定位后才提供精确行号。
- [ ] 收窄置信含义：抽取/推断、人审状态、来源新鲜度分别存储。领域词表匹配属于规则判断，不能让名称命中直接冒充领域事实。

验收：关系两端均存在，证据可回溯；来源/置信的降级可见；更换仓库输入顺序不改变规范化结果。Lite 未支持的 Java 构造明确标记，影响分析显示覆盖限制。

### 5.3 更新与发布一致性（P0）

- [ ] 修 `batch.build_many` 的 root/label 混用，使用稳定 repo_id 键；保存每仓 records，使一个仓变化时复用其余仓记录。
- [ ] 指纹纳入工具/抽取器版本、配置/种子哈希及源内容校验策略；mtime/size 仅用于快速预筛，提供内容校验路径，处理保留时间戳的修改。
- [ ] no-op 前验证必需的 records、graph、coverage 与 manifest 是否完整；缺失或损坏应重建。新增、删除、重命名、移除仓库都有确定处理方式。
- [ ] 同一 generation 的 records、图、coverage、manifest 先写暂存目录，再发布统一快照指针；构建失败保留上一完整快照。图读者只能读到一个完整 generation。
- [ ] 检测扫描期间源变化，重试或明确标为未收敛；同一输出目录限制并发写者。用户笔记不进入扫描输出目录，输出目录不反向摄入。
- [ ] coverage 逐项记载：大文件跳过、读取失败、不支持类型、解析失败、截断、缺依赖；捕获异常不统称“依赖未安装”。

验收：一个仓变化时扫描计数仅包含该仓；配置变化会更新领域；删除/重命名后的 update 与全量构建规范化集合一致；发布中断不会产生“manifest 新、图旧却报告 no-op”。

### 5.4 检索、MCP 与评测基线（P0）

- [ ] 把 `kg_explore` 的 required 移入 inputSchema；校验类型、top_k/depth/预算上下界；增加工具发现与错误响应契约测试。
- [ ] 查询返回 graph generation、indexed_at、source status、coverage gaps。源码更新检测与图热重载分别表达；不能只看 graph.json 就宣称源码最新。
- [ ] 修回放口径：分别记录 raw query Top-5 与 scenario Top-5；场景也固定最多 5 个候选，以预标注实体/证据 ID 评分。8 条旧夹具保留为 smoke，不再命名为业务验收完成。
- [ ] 创建独立评测数据格式（query、入口、预期证据 ID、允许未知/拒答、版本）；输出每条结果与汇总。固定开发/留出集及查询扩展规则，禁止使用期望答案辅助运行时检索。
- [ ] 独立验收集形成至少 20 个需求、10 个故障调查、20 个困难负例，开发集另行保留；先用公开/合成样本接线，真实回放由本地可用的历史材料补齐。真实材料不足时明确标记外部验收未完成。
- [ ] 当前 22 项回归迁移后继续通过；增加上述缺陷的正例和反例，不把已知缺陷的当前行为写成正确契约。

**v0.5 出口**：5.1–5.4 的正确性任务完成；严格指标基线可运行且如实暴露失败项。真实任务质量达标是试点发布门槛，不能用缺少数据或“测试通过”替代。

## v0.6：可复用知识最小闭环

### 6.1 文档与证据检索

- [ ] 将 Markdown/TXT 按标题与受限长度拆片段；可选 PDF/DOCX 保存页码或段落定位。保留原文哈希、解析版本、截断与缺失提示，测试长文后半部也可被查到。
- [ ] 分别召回代码、文档片段、人工知识，再用确定性融合排序；保留 raw/scenario 两个入口，统一可复用的检索服务。中文别名表配置化，可解释为何扩展。
- [ ] 文档检索在 Doc/Chunk 集合内排名；故障调查明确列出“证据”“相关性推断”“待验证”，避免把检索排名称作根因排名。
- [ ] MCP 返回受预算约束的完整证据项：仓库、path、locator、excerpt、哈希、新鲜度、置信；按项裁剪，不切断引用。增加按证据 ID 读取上下文的只读能力。

验收：每个展示结论都有可读取的证据或明确标为无支撑；不同来源可独立检索；知识条目不会仅因代码节点抢占 Top-K 而消失。

### 6.2 保存、审定和再次使用

- [ ] 新增独立人工知识目录：Markdown 正文与版本化 metadata，支持业务说明、架构决策、故障结论；机器图是可重建投影。
- [ ] 定义 Knowledge/Claim/ReviewEvent 的最小 schema。笔记可包含个人说明，事实主张必须记录证据或明确标记 unsupported；接受、争议、撤回与 stale 分别保留。已保存结论引用的片段保留内容寻址快照与原文哈希，使源文件删除后仍可查看历史依据；大附件整份留存作为可选策略。
- [ ] 新增保存入口与预览：草稿 → 校验 expected_hashes → 单写者应用 → 操作记录；冲突时保留双方，不覆盖。新增/更新多文件失败可恢复，重复操作幂等。
- [ ] 实现审定导入与覆盖层：原始推断保留；接受/拒绝/领域纠正参与后续查询；不能靠手改 graph.json 保存人审结果。
- [ ] 来源变更或删除后，将依赖结论标为待复核并列出受影响证据；避免重新扫描时静默消失或自动重新接受。
- [ ] 提供范围明确的 Obsidian 导出：只管理指定输出目录与受管页面，保留用户自行编辑内容；运行第二次不重复造页。先用 Markdown 使用闭环，无需依赖 Obsidian 插件。

验收：用至少 10 条有出处的知识条目走通保存→审定→新会话检索；重建后正文与审定不丢失；冲突保存、中断恢复、重复导入、源变化/删除有可复核结果。无模型配置时仍能手工完成全部流程。

**v0.6 出口**：上述“订单改价”路径与对应故障调查路径均可演示，保存下来的知识能改变下一次检索结果，且依据可回溯。

## v0.7：Java 精度、存储与新鲜度

### 7.1 一个解析后端的选择实验

- [ ] 用同一组公开 Java 仓库与本地许可的试点仓库比较：现有 lite、Codebase-Memory-MCP、CodeGraph、Graphify、直接 tree-sitter Java 适配。仅做有价值的最小探针，不同时建设四套集成。
- [ ] 固定各候选版本，人工标注至少 100 条代表性调用关系；覆盖接口实现、同名/重载、字段别名、嵌套类、跨文件、框架绑定。分别统计 precision、recall、未解析比例、索引时间、内存和部署摩擦。
- [ ] 候选高置信调用 precision 目标 ≥95%，且召回/任务成功率相对 lite 有可解释提升；在达标候选中选维护成本最低的一个。没有候选达标则记录失败样例、保留 lite 的降级提示。
- [ ] 通过 `Extractor` 契约导入 records/evidence；domimap 保留业务框架规则、人工知识、检索体验的控制权。树形语法解析不自动等于类型解析准确。
- [ ] 正式引入前记录 upstream revision、接口、分发方式与相应许可证文件；Graphify 当前仓库包含多种许可证文件，不沿用历史“统一 MIT”的假设。

### 7.2 按测量选择存储与增量

- [ ] 在约定硬件与固定数据集记录构建、冷启动、热查询 p50/p95、RSS 与索引大小；小型夹具和真实规模分别报告。
- [ ] 若 JSON 全量装载、内存或一致性成本成为瓶颈，再用 stdlib sqlite3 承担索引/元数据；FTS5 在 doctor 探测，缺失时提供词法回退。图 JSON 继续可导出，人工知识保持可迁移。
- [ ] 把每仓缓存推进到文件内容哈希与依赖失效传播：覆盖增删改、改名、配置变化、分支切换与 schema 升级；更新与全量结果等价。
- [ ] 实现监听时加入事件合并、队列溢出恢复、周期校验、错误可见性；发布新快照前相关结果显示 pending/stale。

性能建议目标：固定规模约 16 万节点的试点图，热查询 p95 ≤1 秒、冷启动 ≤5 秒、单文件更新到可用 p95 ≤3 秒；必须同时记录硬件与数据规模。这些是待测目标，不是现有承诺；超标先定位再决定实现方案。

**v0.7 出口**：选定后端有可重现结果；结构精度门槛通过；实际采用的增量与监听能力通过等价测试。未触发的数据库迁移任务可以按实验结论关闭。

## v0.8：本地界面与试点发布

- [ ] 最小界面仅覆盖：搜索结果、来源上下文、领域页、知识条目、待审/失效队列；与 CLI/MCP 共用查询和写入服务。默认本地访问。
- [ ] 从真实反馈选择是否需要局部关系图；避免把“全图可视化”作为试点前置条件。
- [ ] 连续使用试点覆盖需求定位、故障调查、知识保存与领域纠正；记录任务完成质量、耗时、人工修正量，而非仅收集节点数量。
- [ ] 完成支持平台的安装、MCP 联调与包内资源检查；没有验证的平台标明未验收。清理包元数据与实际成熟度的差异。
- [ ] 用可审查的公开合成样例构建发布物，验收通过后再执行仓库/PyPI 发布；包构建成功本身不代表业务能力过线。

**发布门槛**：下表质量门槛通过；知识保存可恢复、重建不丢人工数据；支持的平台有安装与最小闭环记录；文档与实现一致。

## 统一质量门槛

| 指标 | 目标与口径 |
|---|---|
| raw query Top-5 | 单独报告 hit@5、MRR 与样本量；不得借用 scenario 结果补分 |
| scenario 需求 Top-5 | 至少 20 个留出历史需求，按预标注 ID 命中率 ≥80%；每个请求最多 5 个主要候选 |
| 故障调查 | 至少 10 个历史案例，相关调查证据/链路前 5 命中 ≥7；区分静态线索与运行时根因 |
| 领域标签 | 抽样最多 100 服务，小样本则全量；准确率 ≥90%，未知/冲突不从分母剔除；报告覆盖率 |
| 无依据问题 | 至少 20 个近义但无证据、跨域混淆、来源已失效等困难负例，明确拒答/保留判断 ≥95%；可回答集单独报告误拒答 |
| 引用完整性 | 展示为有支撑的结论 100% 有可定位证据；审查摘录是否真正支持结论，不能只检查链接存在 |
| 全量/增量 | 固定版本下规范化节点与关系集合相等；忽略生成时间与排序，不容忍漏边误差率 |
| 人工知识 | 重建保留；并发冲突可见；失败保存可恢复；源变化后及时标记依赖结论 |

与关键词/读文件及仅文本检索做同任务对照，报告质量、时间与返回预算；若图未提升效果，优先调整检索/资料组织而非扩展图算法。真实样本暂不可用时，用合成集检查机制，并在结果中注明尚未完成业务验收。
