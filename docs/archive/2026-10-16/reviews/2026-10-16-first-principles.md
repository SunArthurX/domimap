# domimap：从第一性原理推导的改进建议

日期：2026-10-16。状态：**设计建议与取舍依据**。结合当前 v0.4.0 源码、第三版路线、四项能力补充及合成诊断；没有实现下述新能力。

这些建议现已收敛进[生产级知识库主计划](../../../roadmap.md)。本文保留推导与原阶段引用，执行顺序以新主计划为准。

分析目标是回答：知识库怎样让人和 Agent 更快形成正确、适用、可以复核的理解，并以可承受的成本长期维护。

## 1. 先确定产品究竟优化什么

可以用一个概念上的成本账衡量价值：

> 净价值 ≈ 节省的理解与决策成本 + 减少的错误损失 − 接入成本 − 持续维护成本 − 错误结论带来的损失。

这不是已经测量的公式；它约束投入选择。节点更多、读取文件更多、接了更多模型，只有改善上述结果才有价值。

用户每次真正需要的是一组可行动的信息：

1. 当前问题在问哪个系统、版本和范围？
2. 有什么证据，证据具体说明什么？
3. 哪些是已实现行为、需求意图、人工决策或推断？
4. 哪些地方不确定、互相矛盾或尚未检查？
5. 这次得到的解释能否保存，并在条件变化后重新核对？

因此，现有“本地研发知识库，以 Java 多仓切入”的定位合理。主产品单元应进一步明确为：**带适用范围和出处的可复核结论**。文件、符号、图边、文档片段是形成结论的材料，MCP、搜索页、AGENTS/SOUL 是使用入口与行为偏好。

## 2. 当前证据与推演边界

本轮只读取本项目，诊断使用内存合成图和内存 SQLite。未扫描真实业务工作区，未测试上游解析器，也未得到真实用户效果数据。

完整结果见[诊断记录](2026-10-16-first-principles-evidence.json)。

| 观察 | 当前证据 | 可以得出的结论 |
|---|---|---|
| 查询缺少适用范围过滤 | `Searcher.query` 只有 domain 等参数；合成图同时返回 production-v1 与 development-v2，渲染不展示这些 scope | 需要独立的范围契约；不能认为来源哈希或领域标签已解决版本适用性 |
| 字数预算没有限制遍历工作量 | 一个有 2000 个出邻居的领域节点，budget=120，仍先扩展 2000 个再截断输出 | 展示预算和计算预算必须分别限制；不能由短输出推断低计算成本 |
| 重复来源占据主候选 | 11 文档、2 个来源家族的合成图，Top-5 全来自同一原始来源的副本 | 命中文档数量不等于独立信息量，检索需要去重和来源多样性 |
| 时间分数不能替代权威性 | 按现有候选公式，同相关性下，一天前草稿因子约 0.998，一年前仍有效资料约 0.812 | 这是设计反例，说明需要先判断适用性与资料状态；不意味着公式必须取消 |
| 整篇笔记的状态不足以表达局部失效 | 一篇笔记同时记实现归属和退款期限，只有期限依据变化 | 这是模型推演；不同可复核陈述要能分别引用、复核与失效 |
| 文档意图与实现可能不一致 | 订单改价夹具 PRD 声明乐观锁；SQL 没有旧版本条件；模拟两个先读到版本 0 的写入，两次都影响 1 行 | 搜到 price_version 不能证明防覆盖已经实现；这不是对真实生产系统的审计 |

## 3. 第一项优先改进：把适用范围放在排名之前

### 原理

一条知识可以有真实出处、准确引用和最近复核时间，却不适用于当前问题。旧生产版本与新开发分支的差异，就是最简单的反例。

当前 `revision/hash` 能回答“读的是哪份内容”，不能单独回答“用户问的系统正在用哪份内容”。同样，“订单域”无法替代具体仓库、组件、发布版本或运行环境。

### 最小做法

- 查询始终携带当前选定的知识库与 snapshot；响应、搜索页和诊断都清楚显示它们。
- 为来源和结论增加可选 applicability：组件、版本/ref、适用时间；环境映射只有实际登记时才成立。无 Git、无部署信息时显示 unknown，不能根据分支名自行推定生产环境。
- 已知范围先做资格筛选，再计算相关性和时间分数。用户明确问某个版本时，不静默拿其他版本补成当前答案。
- 信息不足但不影响结果时沿用当前工作区默认；存在会改变结论的歧义时，展示候选范围与缺口，让用户选择或提供部分答案。
- 来源注册允许独立的文档文件夹。知识资料不以存在 pom.xml、package.json 或 .git 为接入前提。

### 验收

相同符号、相同文档名在两个版本下允许得出不同结论；版本筛选不会混入另一版本。没有部署映射时不能输出“线上正在使用”的确定说法。默认知识库不能悄悄指向演示夹具。

**投入判断**：这是基本数据与查询契约，应在 WP1 定义、WP3 使用，优先于优化排名权重。

## 4. 第二项优先改进：区分陈述类型，并按陈述引用

### 原理

“需求要求这样做”“源码写了这段逻辑”“系统运行时观察到这样”“团队决定以后这样做”是不同知识。把它们合成一段流畅摘要，会掩盖尚未实现的要求或尚未验证的推断。

本项目有一个现成的评测材料：

- [改价 PRD](../../../../tests/fixtures/mini/docs/改价需求PRD.md)说需要防并发覆盖，并使用 price_version 乐观锁。
- [Mapper SQL](../../../../tests/fixtures/mini/order-service/src/main/resources/mappers/OrderMapper.xml)按 id 更新价格并递增版本，没有比较调用者看到的旧版本。
- [服务方法](../../../../tests/fixtures/mini/order-service/src/main/java/com/example/trade/OrderPriceService.java)忽略 update 的影响行数并返回 true。

在内存执行同一更新语义，两个写入都先观察到版本 0，再依次更新，均成功，最后价格为第二次写入、版本为 2。这个可行的交错顺序已经足以说明：**仅凭展示的 SQL 与方法不能确认有乐观冲突拒绝机制**。夹具不完整，不能据此推断真实系统没有任何其他保护。

理想知识库应该同时报告“需求要求防覆盖”“当前展示的代码没有证明该要求已满足”和“仍需检查的保护位置”，而非把 PRD 当作实现证明。

### 最小做法

保留单条知识记录作为保存单元，在其中用轻量 `claims` 列表表达可复核陈述。每条只需要：稳定 ID、正文、类型、适用范围、支持/反对证据、审定状态和依赖；没有结构化陈述的自由笔记仍可保存，但不能整篇自动标为事实已验证。

类型先限制为少量明确类别：需求/约定、静态实现、运行观察、人工决策、推断。不要求自动拆解所有文档，也不前置一套大型本体或语义模型；首版可由人或客户端明确提交结论。

一篇笔记的两条陈述应可独立处理：期限变更时只把“退款期限”标待核对，归属说明保留自己的依据；修改一条陈述也不能自动接受另一条。

引用可在源版本、位置以外保留原文摘录与短上下文，明确行号/字符位置的坐标体系，避免跨解析器错位。W3C 的[文本引用与位置选择器](https://www.w3.org/TR/annotation-model/#selectors)提供了可借鉴的锚定思想；这里建议使用普通 JSON 字段，不要求引入其全部格式。

### 验收

把上述 PRD/代码差异加入语义验收：命中符号只能算找到材料，输出“已实现乐观锁”需要足够支持；缺少支持应说清。评测同时检查需求和实现的区分，而不只看 Top-5 是否出现 price_version。

**投入判断**：WP1 只预留兼容字段；WP4 实现最小陈述列表。避免先做整篇审定，后来再迁移所有已存知识。

## 5. 第三项优先改进：建立来源家族、权威性与冲突表达

### 原理

同一 PRD 的十份导出、一次 AI 摘要和两个转述，不等于十三份独立证据。新生成的摘要也不应使旧事实自动变新。

权威性取决于问题：解释设计意图应读有效决策或需求；说明静态行为应指向对应源码；声称运行状态则需要对应版本的运行依据。不能制定“代码永远高于文档”或“最近更新永远更可信”的统一规则。

### 最小做法

- 来源记录 source_kind、可确定的状态（例如 draft/approved/unknown）和来源家族；原始出处与摘要保留 `derived_from`。
- 首版先对相同内容与明确派生来源去重；同一来源家族在主候选中折叠，并允许展开副本，不因多份副本提高支持强度。
- 冲突保留并列陈述及范围。只有明确 supersedes、撤回或人工裁决，才把旧版本排除出当前依据；年份更近本身不证明替代关系。
- 推荐顺序是范围/有效性筛选 → 与问题匹配 → 支撑与冲突检查 → 必要的时间降权。权威与相关性不是一个可随意平均的“可信分”。

[W3C PROV-O](https://www.w3.org/TR/prov-o/#description-starting-point-terms)把来源派生与责任归属分开表达，适合借鉴为 `derived_from`、生成活动和复核者等最小字段。这里不建议为此引入 RDF 或推理平台。

### 验收

重复摄入不会让主候选被副本占满；旧来源摘要不刷新原始证据年龄；互相矛盾且范围未厘清的资料显示争议。近期草稿不会只凭时间分数覆盖仍有效的正式约定。

**投入判断**：WP2 保留来源家族与状态；WP3 做精确去重、范围筛选和冲突提示；自动冲突发现、近似重复聚类在数据需要时再增强。

## 6. 第四项改进：按问题使用图，并分别限制计算与上下文

### 原理

查一个字段的位置、追改动影响、理解架构原因，对信息结构的需求不同。简单定位可由词法与精确匹配完成；跨服务路径需要图；解释原因需要文档或已审定决策。

每次都扩展邻居会引入无关内容和成本。当前合成实验还显示，文本最后截短并没有限制已遍历的边数。

### 最小做法

- 公共查询服务区分定位、关系追踪与解释需求。可先用明确模式和简单规则，用户仍可只输入一个问题。
- 初次返回少量主候选、完整出处和不足项；按证据 ID 再取上下文，关系查询再返回有依据的路径。
- 在遍历过程中同时限制 max_nodes、max_edges、max_hops 与时间；单独限制返回字数。达到限额时返回 partial/budget 状态及未覆盖范围，不能先遍历全图再靠截断解决。
- 四客户端与人工页面消费相同结果对象，展示层不同。保持结构化结果和可读文本的兼容出口，不让每个客户端重新推断出处和新鲜度。
- 结构化返回随协商的 MCP 协议能力适配；[MCP 工具规范的 structuredContent](https://modelcontextprotocol.io/specification/2025-06-18/server/tools#structured-content)可作为支持该版本客户端的输出方式，旧客户端使用文本承载同一版本化结果对象。

### 验收

高出度节点也不能突破遍历预算；结果不会半截丢失引用。字段精确查询无需读取大量邻居；跨服务问题能解释路径中每条边的出处。比较“纯文本”和“图加文本”的真实效果，图应有可测的增益。

**投入判断**：WP3 增加边界与分步阅读；不需要前置更大的图数据库或新的 Agent 运行时。

## 7. 第五项改进：让维护成为可完成的工作

### 原理

知识可以长期保存，正确性需要持续维护。时间标签只有在用户知道该检查哪条结论、能看到改变内容、能低成本处理时才有实际作用。

### 最小做法

- 保留 source/evidence/配置 → claim 的显式依赖。来源改变时形成待复核事项，展示旧结论、原证据、变化位置和受影响范围。
- 先按“正在使用且依据已变”“明确过期”“长期未复核”排序，不把所有旧文档一齐推给人。单用户默认由当前使用者处理，不需要先接组织通讯录。
- 每项提供三种基本处理：确认仍适用并绑定新证据、修改/替代结论、撤回结论。缺少支持时保持待复核，不能仅因用户看过就刷新复核时间。
- 同一变化只生成一项可合并的待办；无关文件变化不应把整个知识库标失效。首版可保守标待复核，但要统计这种额外维护成本。
- 加入轻量反馈：找错范围、依据不足、资料过时、仍然有用；反馈关联 query/snapshot/evidence，是否保留原始查询由本地策略明确。点击与使用频率只是价值信号，不是真实性证明。

对推断关系的复核还应绑定目标关系、适用范围及推导配置版本，不能只比较某个源文件的哈希。改变服务映射、规则或 source scope 也可能改变结论。

### 验收

改变一条依据，能定位到受影响的陈述；重复扫描不会重复制造待复核事项。一次确认不能顺带接受无关陈述。用户能在证据变化后完成一次复核并在后续检索看到结果。

**投入判断**：WP4 在已有保存与审定上补依赖和最小队列；自动通知或复杂任务调度待实际需要出现时再引入。

## 8. 第六项改进：验证知识能带走、能恢复、能按意图移除

### 原理

用户愿意长期投入整理，前提是内容不会随索引器替换而丢失，也不会因为误操作无法恢复。这是人工知识的基础生命周期。

### 最小做法

- 可导出知识正文、陈述、适用范围、审定记录及被固定的证据；可恢复到空目录并重建检索。客户端凭证和非必要的整仓源码不进入默认导出。
- 快照有明确的保留与固定规则、占用统计，避免来源持续变化导致磁盘无限增长。
- “重建派生图保留人工知识”与“用户主动删除知识”分别定义。删除操作清理受管检索与派生视图，保留的引用依赖要清楚说明；显式遗忘来源时处理受管副本及备份策略，不能承诺控制外部客户端历史或用户自管副本。
- 产品源码和计划应从实施开始采用版本控制；当前目录没有 Git，可在进入实现时建立。用户知识与原始业务资料单独存放，不能顺带提交到产品仓库。

### 验收

干净目录导入后，笔记、审定、引用与范围保持；删除后搜索不再返回已移除记录；索引损坏可以重建，人工知识有独立恢复路径。

**投入判断**：WP4 将一次导出/恢复演练作为保存功能的验收，基础保留清理随快照实现；更复杂的备份介质和共享同步按需求增加。

## 9. 第七项改进：用真实任务收敛投入

### 原理

接入四客户端、人工搜索、轻量人设和时间衰减都已是明确需求，应继续保留。它们是否真正有用，需要用实际工作验证。继续增加方案条目会产生机会成本，目前产品代码仍是 v0.4.0。

### 第一批验证

先选一个允许使用的真实工作区，固定 10 个真实问题，其中包含版本差异、需求/实现不一致、重复来源和确实没有依据的情况。它们用于发现问题，不能作为总体通过率的统计证明。原先更大的独立验收集继续保留为试点目标。

逐项记录：

| 指标 | 解释 |
|---|---|
| 首次得到可核验证据的时间 | 包含接入、选知识库、检索和打开来源的成本 |
| 任务结论正确与适用 | 分开看答案真假、范围是否正确、必要依据是否齐全 |
| 错误确定结论 | 尤其是把需求当实现、把别的版本当当前、把多个副本当多份支持 |
| 重复任务成本 | 保存后换会话再问，是否减少重新探索且保持依据正确 |
| 维护负担 | 有效使用带来多少额外确认、误报或人工修正 |
| Agent 成本 | 同任务比较工具调用、返回量、耗时；在实际客户端记录可得到的 token 数据，不挪用上游宣传数字 |

同时做移除某层的对照：只文本、文本加图、再加人工结论。它有助于判断下一步应修摄入、调整检索、补图关系还是补知识维护，避免把所有问题都交给更大模型。

## 10. 建议如何放入现有路线

这些建议以补齐契约和验收为主，不增加新的大平台或新版本承诺。

| 优先顺序 | 建议 | 落点 |
|---|---|---|
| 首先 | 查询与结论的适用范围；显示当前知识库/snapshot | WP1 最小契约，WP3 筛选与展示 |
| 首先 | 区分需求/实现/观察/决策；加入 PRD/SQL 不一致反例 | WP1 兼容字段，WP3 验收，WP4 轻量 claims |
| 随首个可用检索 | 来源家族、精确去重、明确争议与遍历预算 | WP2/WP3 |
| 随保存闭环 | 按陈述复核、最小反馈、导出与恢复 | WP4 |
| 用真实任务决定 | 自动语义抽取、近似去重、复杂调度与更大索引后端 | WP5 条件增强 |

第一批实施仍从现有 WP1 开始，但在冻结 schema 前处理范围与陈述兼容性。四项已接受的用户能力保留在第三版计划；本文作为建议依据，不把尚未实现的能力勾成完成。

目标是一条可以重复完成的实际路径：找对适用范围 → 找到必要证据 → 保留分歧和未知 → 形成可复核解释 → 保存 → 再次使用 → 条件变化后修订。
